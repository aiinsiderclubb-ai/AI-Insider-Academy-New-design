# Как это работает

## Путь клиента

```
заявка ─► Webhook (сайт, портал, CRM) / Telegram
            │
          Config ─► Guard In ── токен, лимиты, карта, «позовите риелтора»
            │
          AI Agent + память (16 сообщений) ──► инструменты:
            │   update_lead → Leads (балл, риелтор, чего не хватает)
            │   search_listings → Listings (до трёх объектов с причинами)
            │   check_viewing_slots → календарь риелтора объекта
            │   book_viewing → календарь + Viewings + Leads + Telegram риелтору
            │   handoff_to_human → Telegram агентства
            ▼
          Guard Out ── выдуманный объект, обещания, утечка, пустой ответ
            │
          Log ─► ответ на сайт / в Telegram

каждый день 10:00 ─► Follow-up: напоминания клиентам, список звонков и просмотров риелторам
```

1. **Вход.** Заявка с сайта, портала или из CRM приходит в Webhook, сообщение клиента — в Telegram Trigger.
2. **Guard In** проверяет токен и лимиты, вырезает номер карты, помечает попытки подмены правил, переводит «позовите риелтора» человеку без модели и добавляет к сообщению канал, контакты и объект из заявки.
3. **AI Agent** ведёт разговор по инструкции `agent/system-prompt.md` и вызывает инструменты.
4. **Guard Out** проверяет ответ и пишет трассу в `Log`.
5. **Follow-up** — отдельная ветка без модели: по расписанию читает `Leads` и `Viewings`.

## Что решает код, а не модель

| Решение | Где |
|---|---|
| балл лида и сегмент | Lead Upsert |
| к какому риелтору идёт лид | Lead Upsert (район, тип сделки, хэш диалога), Booking Rows (риелтор объекта) |
| какие объекты подходят и почему | Match Listings |
| свободное время | Slots: часы, встречи риелтора, зазор, «не раньше чем через», окно записи |
| сказал ли клиент «да» | Booking Plan — по тексту последнего сообщения клиента |
| нет ли уже такой записи и свободно ли время | Booking Decide |
| назвал ли агент несуществующий объект | Guard Out |
| кому и когда напомнить | Plan Follow-ups |

Модель ведёт разговор и выбирает, какой инструмент вызвать. Факты, время и решения с последствиями — у кода.

## Инструменты — ветки того же воркфлоу

Узел инструмента вызывает этот воркфлоу (`$workflow.id`), вызов приходит в Tool Call, проходит Config и Kind и попадает в Tool Switch. Часть полей заполняет модель, часть — воркфлоу: сессия, канал, источник, контакт клиента и **последнее сообщение клиента** — по нему Booking Plan и проверяет «да».

## Состояние

- Память разговора — 16 последних сообщений на `session_id`, в памяти n8n.
- Лимиты, пауза после передачи и номера объектов, которые агент уже показывал в диалоге, — в статических данных опубликованного воркфлоу.
- Всё, что нужно агентству, — в таблице: `Leads`, `Viewings`, `Log`.
