# Сборка и запуск

## D-01. Сборка сценария

**Зачем:** Собрать сценарий так, чтобы его мог поддерживать другой человек.

**Когда:** Техническое задание согласовано.

**Отвечает:** Инженер по автоматизации

### Шаги

1. Создать сценарий на аккаунте клиента, не на своём.
2. Назвать узлы по действию: «Создать сделку в CRM», а не «HTTP Request 3».
3. Секреты хранить в учётных данных платформы, не в тексте узлов.
4. На каждый внешний вызов — повтор при сбое и ветка ошибки.
5. Добавить журнал: что пришло, что решили, что отправили.
6. Оставить заметку в начале сценария: назначение, владелец, дата.

### Готово, когда

- [ ] Сценарий на аккаунте клиента
- [ ] Ветка ошибок с уведомлением
- [ ] Журнал запусков
- [ ] Узлы названы по действию

### Частые ошибки

- Ключи в теле запроса
- Сценарий без обработки ошибок

## D-02. Промпты и проверка качества

**Зачем:** Получить стабильный ответ модели на реальных данных.

**Когда:** Собран каркас сценария.

**Отвечает:** Инженер по автоматизации

### Шаги

1. Написать промпт: роль, задача, входные данные, правила, формат ответа, что делать при нехватке данных.
2. Требовать структурированный ответ (JSON) там, где его читает следующий узел.
3. Собрать набор из 30 реальных примеров с правильным ответом.
4. Прогнать набор, записать долю верных ответов.
5. Править промпт, пока доля не достигнет согласованного порога.
6. Сохранить версию промпта и результат прогона.

### Готово, когда

- [ ] Набор тестовых примеров
- [ ] Доля верных ответов не ниже порога из описания работ
- [ ] Версия промпта сохранена

### Частые ошибки

- Проверять на трёх придуманных примерах
- Менять промпт без повторного прогона

## D-03. Тестирование перед запуском

**Зачем:** Найти сбои до клиентов клиента.

**Когда:** Сценарий собран.

**Отвечает:** Инженер, приёмка — руководитель проекта

### Шаги

1. Прогнать типовой случай из каждого канала.
2. Прогнать исключения: пустое поле, длинный текст, другой язык, дубль, вложение.
3. Отключить по очереди каждую внешнюю систему и проверить, что приходит уведомление.
4. Проверить, что тестовые данные не уходят реальным клиентам.
5. Показать прогон клиенту и получить письменную приёмку.

### Готово, когда

- [ ] Протокол тестов с результатами
- [ ] Письменная приёмка клиента

### Частые ошибки

- Тестировать только «счастливый путь»

## D-04. Запуск

**Зачем:** Включить без сюрпризов и иметь путь назад.

**Когда:** Тест принят.

**Отвечает:** Руководитель проекта

### Шаги

1. Выбрать время запуска вне пиковых часов клиента.
2. Сохранить копию сценария и прежних настроек.
3. Включить на часть потока или на один канал.
4. Первые два часа смотреть каждый запуск.
5. Через сутки включить на весь поток.
6. Сообщить клиенту: что включено, куда смотреть, кому писать.

### Готово, когда

- [ ] Сценарий работает на полном потоке
- [ ] Есть копия для отката
- [ ] Клиент уведомлён

### Частые ошибки

- Запуск в пятницу вечером

## D-05. Передача и обучение

**Зачем:** Команда клиента должна уметь пользоваться и знать, что делать при сбое.

**Когда:** Сценарий работает.

**Отвечает:** Руководитель проекта

### Шаги

1. Написать инструкцию на 2 страницы: что делает система, что делает человек, что делать при ошибке.
2. Записать видео на 10 минут с экрана.
3. Провести сессию 45 минут с теми, кто будет работать с системой.
4. Передать реестр доступов и список расходов на сервисы.
5. Подписать акт и выставить вторую часть.

### Готово, когда

- [ ] Инструкция и видео у клиента
- [ ] Сессия проведена
- [ ] Акт подписан

### Частые ошибки

- Передать сценарий без инструкции «что делать, если сломалось»
