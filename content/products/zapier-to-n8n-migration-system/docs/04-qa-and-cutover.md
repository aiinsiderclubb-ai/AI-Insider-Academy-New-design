# Проверка и переключение

## Чек-лист перед параллельным прогоном

- [ ] Все шаги из `steps.csv` перенесены, отмечены в `migration-map.csv`.
- [ ] Error Workflow назначен.
- [ ] Учётные данные — клиентские, не ваши.
- [ ] Часовой пояс воркфлоу задан.
- [ ] Прогон на 3–5 реальных примерах: результат совпадает со старой системой.
- [ ] Необратимые действия (письма клиентам, счета, платежи, удаление) на время прогона заменены записью итога в воркфлоу сверки.

## Параллельный прогон со сверкой

Воркфлоу **Parallel Run Log** принимает итог каждого события от обеих систем и сравнивает.

**В старой системе** (в конце zap'а или сценария) добавьте шаг Webhooks by Zapier → POST / Make HTTP → Make a request:

```json
{ "token": "ВАШ_ТОКЕН", "flow": "Заявки с сайта", "key": "{{id заявки}}", "system": "old", "result": { "email": "…", "deal_stage": "…", "owner": "…" } }
```

**В n8n** — последний узел HTTP Request на тот же адрес с `"system": "new"` и теми же полями `result`.

Правила:

- `key` — одинаковый идентификатор события в обеих системах: id заявки, номер заказа, id письма.
- В `result` — то, что важно для бизнеса: кому назначено, какой статус, какая сумма. Не всё подряд.
- Поля, которые всегда разные (id записей, время), — в `ignore_fields` или `compare.<поток>.ignore`.

Каждое утро — сводка: сколько событий, процент совпадений, есть ли потерянные, «можно переключать» или «рано». Порог — `ready_min_events` событий за `ready_days` дней без единого расхождения.

## Переключение

`templates/cutover-runbook.md`. Коротко:

1. Время — рабочие часы клиента, не пятница вечером.
2. Включить необратимые шаги в n8n.
3. Переключить адреса вебхуков у отправителей.
4. Выключить zap/сценарий (не удалять!).
5. Проверить первые 3 события руками.
6. Через 7 дней без сбоев — удалить в старой системе, понизить тариф.

## Откат

Старая автоматизация не удаляется неделю. Откат — включить её и вернуть адрес вебхука. Держите список адресов «старый → новый» в `migration-map.csv`.
